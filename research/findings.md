# Verified findings, limitations and next steps

## Scope and evidence

The repository was initially an empty scaffold: no old model, feature cache, evaluator, or submission writer existed in this checkout. We inspected the nine focus sites and the official problem page, restored hash-pinned public mirror files, and ran `scripts/audit_nine_sites.py`. Byte hashes prove consistency with the selected mirror, not that the files were downloaded directly from DrivenData. The focus scores are **USER-REPORTED / UNVERIFIED**: no organizer submission receipts connect them to these exact bytes. A public leaderboard snapshot is official for the public leaderboard, but it is not a receipt for these files. No private ground truth or actual current weekly quota was accessible.

## Why the reported GEMSDOE32 result may be stronger

The measured masks establish an exact relation: the pinned GEMSDOE32 H33-B2 support is the pinned GEMSDOE25 D2.8 support with all 6,436 dots at Euclidean distance ≤ 2 pixels from the mirrored catalogue removed; the remaining support has 37,654 pixels and the XOR is zero. This is a lineage fact, **not** proof of the organizer score or of causal improvement. GEMSDOE25 and GEMSDOE30 have identical in-footprint positive support despite different file hashes and outside encodings. In the measured nine-file comparison, all nine have greater than 70% directional 3-pixel overlap with another focus-site best. The summary and exact immutable links are in [the audit](../evidence/portfolio_audit.json).

The [official metric](https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/#performance-metric) weights nearest fault credit with a triangular kernel up to 300 m. It uses α = 0.2 for false-positive mass and β = 0.8 for false-negative credit. Thinning a long candidate line into separated dots can reduce prediction mass while retaining some nearby truth credit; dropping near-catalogue predictions can reduce false-positive mass if hidden truth is sparse there. Both are plausible **explanations**, not established causation: the test labels and matched submission receipts are unavailable. The organizer says the **known pixels** are excluded, not a blanket 200 m or 300 m buffer ([staff clarification](https://community.drivendata.org/t/scoring-clarification-are-known-usgs-ingenious-faults-masked-when-scoring-and-are-they-in-the-final-round-label-set/11516/2)). Blanket deletion near known faults is an empirical gamble that may miss genuine new faults. The organizer also states that public score components are pooled before the index is computed ([clarification](https://community.drivendata.org/t/leaderboard-aggregation-pooled-over-public-test-pixels-or-mean-of-per-chunk-scores/11550/2)).

We cannot say this candidate can beat the reported 0.2778 or today's leaderboard. A catalogue hide-and-recover result is a different target from new expert-mapped faults, and a fitted projection is not an observed competition score.

## Irregularities

1. **Literal uniqueness is unsatisfiable under the shared support definition.** A registered [17GEMSDOE continuous surface](https://github.com/buffedlizard55-lab/17GEMSDOE/blob/6fc71d19d49dca4960d5434bd81b6dd06fcc030a/docs/downloads/17GEMSDOE_E-proba-multiscale_20260930T044527Z.tif) is positive on every footprint cell. The shared template treats finite positive cells as support, so any nonempty in-footprint dot set is 100% within 3 pixels. The [shared-template check](../evidence/shared_tool_checks.json) independently confirms the universal blocker. Calling this result “geological duplication” would be wrong; changing the comparison rule without authorization would also be wrong. A separate 5-pixel lattice alone bounds the overlap of a 37,654-dot candidate to at least 82.34%. We stopped before placement, holdout, and TIFF creation; no competition slot was used. These witnesses establish failure, not an exhaustive registry scan.
2. **Lane absent.** The prompt mentions a single method paragraph, but none names a specific lane. RCSO is a proposed idea, not an assigned lane. No new submission is approved.
3. **Mirror sample anomaly.** The mirror called `sample_submission.tif` has exactly the same 60,988 positive footprint cells as `labels.tif`; the official problem page describes the provided sample as predicting total fault absence. We independently measured the zero-XOR support relationship but cannot establish the mirror's origin or why it differs. We used this file only for its reference grid/finite footprint, never as label-independent truth.
4. **Range error cause not established.** Several historical `-nan` rasters contain NaN outside the mirror footprint. NaN may be relevant to a portal range error, but the rejected bytes and organizer validator implementation are unavailable. A whole-array-finite encoding is an extra local precaution, not proof of acceptance. The official format describes null/NaN outside bounds; do not claim that zero-outside is accepted until the organizer confirms it.
5. **Unsafe sibling CLI wrappers for soft predictions.** At pinned [GEMSDOE32 `scripts/evaluate_holdout.py`](https://github.com/buffedlizard55-lab/GEMSDOE32/blob/07806249f4ed3efe70b4fbf866183c32392b7853/scripts/evaluate_holdout.py), raster inputs are converted to `isfinite(arr) & (arr > 0)` before scoring. At pinned [GEMSDOE32 `scripts/submission_writer.py`](https://github.com/buffedlizard55-lab/GEMSDOE32/blob/07806249f4ed3efe70b4fbf866183c32392b7853/scripts/submission_writer.py), the same conversion binarizes predictions and can hide invalid positive values. Neither wrapper is safe for general probability fields. This checkout cannot patch the upstream repository on the session branch, so the issue remains **unfixed upstream**. Instead we tested and reference the pinned shared [`vendor/gems57/evaluate_holdout.py`](https://github.com/buffedlizard55-lab/GEMSDOE32/blob/07806249f4ed3efe70b4fbf866183c32392b7853/vendor/gems57/evaluate_holdout.py) and [`submission_writer.py`](https://github.com/buffedlizard55-lab/GEMSDOE32/blob/07806249f4ed3efe70b4fbf866183c32392b7853/vendor/gems57/submission_writer.py), which preserve soft values / reject invalid ranges on our fixtures. Their passing tests do not prove a candidate scientifically valid.
6. **Site verdicts differ.** Some sibling sites say a recent candidate is upload-ready after a smaller registry audit; that cannot satisfy the present literal any-registry rule. Other pages explicitly exempt space-filling priors. No such exemption has been authorized here.

## Practical next steps

- Decide and document whether “dots” excludes continuous probability surfaces and calibration lattices. If revised, maintain both the literal and representation-aware results, index all accessible prior rasters, fail on missing files, and retain rank correlation for continuous surfaces. No amount of automatic retuning can meet the current definition.
- Assign the one method lane. Freeze it and ≤3 experiments, restore the pinned cached stack, run leakage canaries, derive all catalogue features only from visible faults, use buffered whole-segment spatial folds, and report pooled HOLDOUT-DTI with version, positive count and paired 95% CI against the strongest same-fold baseline. Do not spend a weekly slot without a separate selector.
- Fix and test the two probability-binarizing wrappers in their upstream shared template, not a private fork. Re-verify official sample bytes after legitimate competition access. Download or access the actual features only under the competition terms; no credentials should enter this repository.
- Refresh the leaderboard and site snapshots, and never turn user-reported values or model projections into organizer-confirmed scores. The official challenge target is faults associated with geothermal systems, not direct confirmation of a vent or a commercially viable resource.
