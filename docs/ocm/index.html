Why did GEMSDOE32 score 0.2778 — and can we beat it?

  1. It is the pruned member of one family, not a different science. Byte-decoding shows GEMSDOE25 and GEMSDOE30 are the same array; B2 (GEMSDOE32) is that 44,090-dot mask with dots within 2 px of the mapped catalogue removed (37,654 dots). Removing ~6,400 catalogue-adjacent dots took the USER-REPORTED score 0.2600 → 0.2778. The official metric masks known-fault pixels, so those dots could not earn TP and only paid FP price — pruning frees budget. (MEASURED lineage + official masking rule; causation is an inference.)
  2. The whole 0.245–0.278 cluster is one prior at different budgets/prunes (measured ≥86.7% mutual halo). Score differences inside the cluster are budget/pruning, not method quality.
  3. Can we beat 0.2778 today? Not demonstrated. The local hide-and-recover instrument scores the INVERSE of the leaderboard task (it recovers *mapped* faults, which scoring masks): on it, B2 itself scores 0.0044 and our off-catalogue OCM scores ~0 by construction, while uniform random dots score ~0.043. So the instrument cannot rank off-catalogue candidates — measured, evidence/ocm_holdout_20261031.json.
  4. What would actually raise the ceiling (roadmap): (a) feedback-driven prior refinement using public-leaderboard rounds (the only true supervision for unmapped faults); (b) H2 signed edge-pair veto to remove intrusive-contact false positives from emission; (c) external hydrothermal layers (USGS DGDS springs/sinter/heat-flow) as reweights; (d) spatial-block ML on the 19-band stack — fleet ML attempts so far scored poorly (0.018–0.044 USER-REPORTED).
