Why GEMSDOE32 B2 (0.2778) led the historical sites — and what can be concluded

All figures below are user-reported claims from the sites, not organizer receipts.

No organizer receipt

Measured lineage, not a causal score explanation. A repository byte audit shows GEMSDOE25 and GEMSDOE30 decode to the same in-footprint array; GEMSDOE32 B2 is that same dotted-ridge family after removing 6,436 near-catalogue dots; GEMSDOE36 is B2 plus 1,200 dots. GEMSDOE24, GEMSDOE28 and GEMSDOE31 are also in this family (100.0% near-duplicate overlaps in the pinned audit).

PhD-level assessment of the mechanism. The leaderboard truth is faults absent from the public USGS/INGENIOUS catalogue; known catalogue pixels are excluded from scoring. Dots placed on or near catalogue traces therefore add false-positive mass without truth credit. Pruning near-catalogue dots (B2 = D2.8 minus those dots) concentrates probability on off-catalogue faults — the plausible reason the family scores 0.2449–0.2778 while GEMSDOE36, which re-adds 1,200 dots, scores slightly lower at 0.2750. None of this is proven: hidden labels and an organizer receipt for the exact submitted bytes are unavailable, so 0.2778 cannot be attributed to pruning, and no forecast for a new raster can be made from it.

Can we beat 0.2778? Unknown. This project's new candidate is deliberately not another dotted-ridge raster: it targets stepover/relay apertures (facing fault-end pairs 3–12 px apart), a different uncatalogued structural process, with the same off-catalogue dot discipline (dots >600 m from visible traces). Its only measured evidence is the holdout proxy below; the holdout-DTI proxy has previously been found uninformative for this leaderboard. Treat the estimate as a projection, not a score.

How to make a submission to the contest

Official submission page: DrivenData GEMS Prize — make new submission. One single-band GeoTIFF (.tif), or a .zip containing one GeoTIFF.

  1. Enroll and sign in at the GEMS Prize on DrivenData; read the current rules and check your remaining weekly quota on the submission page.
  2. Download the exact approved file. Use the new GeoTIFF above (or its ZIP containing only that GeoTIFF). Verify its SHA-256 (ddb4e238…574197fc) against this page after download. Do not download a historical or research-only file expecting a fresh result.
  3. Confirm the format locally first. The official format requires EPSG:32611, 100 m, shape 3730 × 3292, one float32 band, and predicted values in [0, 1]. This file is zeros outside the footprint and has no NaN anywhere — the [0,1] portal error some users hit is caused by NaN, infinity, negatives, or values above one in the rejected bytes, not by this file. A local check is not organizer acceptance.
  4. Submit on DrivenData. Submit → Make new submission; choose the TIFF or the single-TIFF ZIP.
  5. Name and note. Use a unique submission name and a short note (at most 140 characters, e.g. "relay-aperture off-catalogue dots 30k cells, stepover nodes >600 m from catalogue traces") so you can tell submissions apart later.
  6. Keep the organizer's receipt. Record filename, SHA-256, note, timestamp and result. A local HOLDOUT-DTI projection is never a live score.
Important. Predicted values must be in range [0, 1]. Never upload NaN or values outside [0, 1]. This project's TIFF is finite everywhere and in [0, 1] inside and outside the footprint. The final accept/reject decision belongs to the organizer portal; this repository does not hold DrivenData credentials and spends no submission slot.
