Step-by-Step DrivenData Contest Submission Procedure

Matches the exact DrivenData New submission portal form (Competition #306 ↗ · Official Rules PDF ↗).

5 Steps
  1. Verify Automated Promotion & Weekly Allowance (`≤ 3` Submissions / Rolling 7 Days): Check the top banner and JSON Run Card (`status == "promote"` and `ok_to_submit == true`), and confirm remaining weekly submissions on DrivenData before uploading. Never upload historical focus-site files (`GEMSDOE24..36`) or `DO NOT SUBMIT` research builds.
  2. Download the Single-Band `.tif` or Single-Member `.zip` & Check SHA-256: DrivenData accepts either a single-band `float32` GeoTIFF (`.tif`) or a `.zip` containing **only** that single `.tif` at the archive root (no `__MACOSX` or sidecar `.json`). Verify locally with `sha256sum <file>` against the Run Card's `raster_sha256`.
  3. Confirm Automated Read-Back Format & `[0, 1]` Receipt (Zero Human Guesswork): Every emitted raster is automatically reopened from disk by `src/wbggems/validate.py` (`inspect_tif(..., strict_all_finite=True)`) to verify:
    • CRS = EPSG:32611 (WGS 84 / UTM Zone 11N, epsg.io/32611 ↗)
    • Shape = (3730, 3292) (`12,279,160` pixels at `100.0 m` resolution)
    • Transform = (100.0, 0.0, 243350.0, 0.0, -100.0, 4508550.0)
    • Bands = 1, dtype = float32, nodata = None
    • nan_total = 0, inf_total = 0, below_zero = 0, above_one = 0 across all `12,279,160` pixels (both inside the `5,167,373`-cell footprint and across all `7,111,787` exterior cells, filled with exact `0.0`).
  4. Upload on DrivenData → `Submissions` → `New submission`:
    • Under File to submit (Choose File), select the verified `-zeros.tif` (or its single-file `-zeros.zip`, `~145 KB` Deflate-compressed).
    • Under Note (optional), paste the Run Card's unique `≤140`-character `submission_note` so your team can link every leaderboard row to its exact Git commit and SHA-256 hash — for example:
      WBG2-GVCD 100%OOF 72f Vent+Stress+ComCat DualCELF 37400d (44%>32px) HOLDOUT-DTI=0.1759 (`86` chars).
    • Click Submit and wait `~30–90 seconds` for automated DrivenData scoring.
  5. Record the `ORGANIZER-CONFIRMED` Receipt: Copy the exact returned public DTI score, submission timestamp (UTC), filename, and SHA-256 into the repository ledger labeled strictly as ORGANIZER-CONFIRMED. Never record a `HOLDOUT-DTI` or `EMPIRICAL-ESTIMATE` as a live score.

Why `"Predicted values must be in range [0, 1]"` Happened — and How It Is Fixed

Root-cause forensic diagnosis across 499 audited GeoTIFFs.

Root Cause #1 (Exterior `NaN` Fill): Across our 8-org byte audit, `189+` historical GeoTIFFs (including `GEMSDOE24`, `GEMSDOE25`, `GEMSDOE27`, `GEMSDOE28`, `GEMSDOE31` `-nan.tif` files) wrote IEEE `NaN` across the `7,111,787` pixels outside the study polygon. Any portal validator evaluating `!(arr >= 0.0 && arr <= 1.0)` over the raw `3730×3292` buffer without masking `NaN` immediately rejects the upload with: "Predicted values must be in range [0, 1]".

Root Cause #2 (Interior NoData Masking): Rejected parallel artifact `wbg2-h1-stepxasym` (`efd46877`) left `5,132,809` interior footprint cells masked as NoData.

Root Cause #3 (Unclipped Logits / Interpolation Overshoot): Uncalibrated regression or bicubic resampling can emit `-1e-7` or `1.0000002`.

Automated Fix in `WBGGEMSDOE2`: `submission_writer.write_submission` writes `0.0` outside the footprint with `nodata = None` (`-zeros.tif`), zero-masks `existing_faults.tif`, and `inspect_tif(..., strict_all_finite=True)` reopens the written GeoTIFF bytes and fails closed if even **1 pixel out of 12,279,160** is `NaN`, `Inf`, `< 0.0`, `> 1.0`, or NoData-masked.
