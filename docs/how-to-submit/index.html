Step-by-Step DrivenData Contest Submission Procedure

Matches the DrivenData New submission portal form (Competition #306 ↗ · Official Rules PDF ↗).

5 Steps
  1. Check your weekly allowance. Sign in to DrivenData, open this competition's submission page, and confirm your remaining submissions (up to 3 automated scorings per rolling 7 days, subject to the platform's current limit). This repository spends no slot and cannot check your quota for you.
  2. Download the single-band `.tif` (or a `.zip` containing only that TIFF) and check SHA-256. Verify locally: sha256sum wbg-relay-aperture-4727dots-20261031T011356Z-574197fc-zeros.tif must print ddb4e2382ff39c139c90e2de068a8615e939a66f77fbede253a1aaa480b83a33. Never upload historical focus-site files (`GEMSDOE24`–`GEMSDOE36`) or `DO NOT SUBMIT` research builds.
  3. Confirm the automated read-back format and `[0, 1]` before uploading. This TIFF was re-read from disk and verified: CRS = EPSG:32611; shape = (3730, 3292); transform = (100.0, 0.0, 243350.0, 0.0, -100.0, 4508550.0); 1 band, float32, no nodata band; 0 NaN / 0 Inf / 0 below-zero / 0 above-one across all 12,279,160 pixels (footprint and exterior). The exterior cells are exact `0.0`, which avoids the `[0, 1]` portal rejection.
  4. Upload on DrivenData → Submissions → New submission. Under File to submit (Choose File), select the verified `-zeros.tif`, or its single-file `-zeros.zip`. Under Note (optional), paste a unique ≤140-character note linking the leaderboard row to this exact artifact, e.g.:
    relay-aperture off-catalogue dots, stepover nodes >600 m from catalogue traces, 4727 cells (`94` chars).
    Click Submit and wait for automated DrivenData scoring.
  5. Record the `ORGANIZER-CONFIRMED` receipt. Copy the returned public score, submission timestamp (UTC), filename, and SHA-256 into your ledger labeled strictly as `ORGANIZER-CONFIRMED`. Never record a `HOLDOUT-DTI` projection or an empirical estimate as a live score. Select one final submission for both prize rounds before the deadline.

Why `"Predicted values must be in range [0, 1]"` happened — and how this file avoids it

Root-cause checklist against the rejected-bytes pattern you reported.

Exterior `NaN` fill (most common cause). Many historical GEMSDOE `-nan.tif` files wrote IEEE `NaN` across the 7,111,787 pixels outside the study polygon. A validator evaluating `!(arr >= 0.0 && arr <= 1.0)` over the raw 3730×3292 buffer without masking `NaN` rejects the upload with "Predicted values must be in range [0, 1]". This file has no NaN anywhere: exterior cells are exact `0.0`.

Out-of-range interior values. `-1e-7`, `1.0000002` or unclipped logits from interpolation overshoot also fail. This file is strictly binary `0.0` / `1.0` inside the footprint.

Interior NoData masking. Rejected parallel artifacts left millions of interior cells masked as NoData. This file has no masked interior cells.

What a local check does and does not prove. The local validator reopens written bytes and fails closed on any non-finite or out-of-range cell. It confirms CRS, shape, transform, band count, dtype and range. It does not prove the DrivenData portal will accept the file — only organizer submission does that.
